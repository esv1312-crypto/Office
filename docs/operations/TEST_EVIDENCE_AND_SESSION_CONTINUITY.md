# AI-ОФИС: правила фиксации тестов и продолжения работы

## Источник правды

- Текущая точка остановки и следующий шаг: [AI_OFFICE_SESSION_HANDOFF.md](./AI_OFFICE_SESSION_HANDOFF.md).
- Подробные первичные доказательства: конкретные GitHub Actions run/job logs и artifacts, плюс Render deploy/events/logs.
- История чата не является единственным хранилищем состояния проекта.

## Перед каждой проверкой

1. Прочитать session handoff.
2. Прочитать актуальный SHA ветки `main` и последние workflow runs.
3. Прочитать Render service/deploy/events и выяснить, какой SHA действительно работает на production.
4. Выбрать тест, подходящий именно к текущему состоянию. Не повторять пройденное без причины.
5. Если GitHub и Render на разных SHA, явно отметить это в плане проверки.

## После каждого теста

В журнале сессии зафиксировать минимум:
- дату и время UTC;
- название workflow/теста и тип окружения;
- branch + commit SHA;
- production deploy ID/SHA, если применимо;
- run ID и прямые ссылки на workflow/job logs/artifacts;
- итог каждого отдельного check, включая пропущенные;
- краткое объяснение фактического результата;
- незакрытые риски и следующий шаг.

Статусы:
- **PASS** — проверка реально выполнена, все критерии пройдены, evidence доступно.
- **FAIL** — проверка реально выполнена и конкретный критерий не пройден; приложить ошибку.
- **NOT VERIFIED** — проверка не запускалась, запуск не состоялся или доказательств недостаточно.
- **STALE** — результат относится к старому SHA/окружению и не доказывает состояние текущего production.

Не считать зелёный локальный тест доказательством production, не считать успешный deploy доказательством работы fallback, и не считать назначенную модель фактически использованной моделью без подтверждающих данных.

## Автоматизация evidence

- GitHub Actions уже хранит run/job logs; для важных тестов сохранять нормализованный JSON summary и диагностические файлы как artifacts с понятным именем и сроком хранения.
- Live workflow должен сохранять итог каждого независимого check даже при частичном отказе; secrets и заголовки авторизации никогда не записывать в artifacts.
- Если автоматическое обновление handoff из workflow добавляется позже, оно должно избегать бесконечных push-trigger loops и не запускать production audit при каждом изменении документа.
- После ручных проверок обновлять handoff в отдельном commit/PR. Не делать запись в журнал на основании предположения.
- Предпочитать ветку и PR для изменений workflow/документации, а не незаметные изменения production.

## Правило передачи новому чату

Новому чату достаточно начать с:
1. открыть handoff;
2. перепроверить GitHub main SHA и последний production SHA;
3. сверить свежие результаты Actions;
4. продолжить с поля «Следующие шаги»;
5. после завершения обновить handoff и сохранить ссылки на evidence.

Так мы уменьшаем повторы и всегда отличаем, что сделано, что доказано, а что ещё предстоит проверить.
