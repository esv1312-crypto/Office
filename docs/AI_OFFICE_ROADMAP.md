# AI-ОФИС — план доведения до первого автономного MVP

## Цель MVP

Пользователь даёт одну задачу. Офис сам:
1. принимает задачу;
2. формирует план;
3. делегирует подзадачи подходящим сотрудникам;
4. выполняет реальные действия через инструменты;
5. отдельно проверяет результат;
6. при ошибке исправляет и запускает повторную проверку;
7. сохраняет доказательства;
8. показывает весь цикл в Live Monitor;
9. завершает задачу только после успешной проверки.

## Жёсткий порядок работ

### Этап 1 — Task/Orchestration Contract
- единая модель Task и Subtask;
- parent/child связи;
- состояния и переходы;
- события жизненного цикла;
- идемпотентность и безопасное завершение;
- API для создания и чтения задач;
- базовый оркестратор без реальных внешних действий.

Критерий готовности: одна входная задача создаёт управляемый граф задач и корректно отражает его состояние.

### Этап 2 — Delegation
- руководитель формирует структурированный план;
- выбирает сотрудника по роли/навыкам;
- создаёт подзадачи;
- ждёт результаты подзадач;
- собирает итог.

Критерий готовности: задача автоматически проходит chief → workers → chief.

### Этап 3 — Tool Gateway
- единый Tool Router/Policy;
- GitHub;
- shell/CI только через разрешённые операции;
- безопасные таймауты;
- журнал каждого tool call.

Критерий готовности: сотрудник реально меняет проект через разрешённый инструмент, а офис знает результат операции.

### Этап 4 — Verification
- отдельный Verifier;
- проверка не тем же контекстом, который выполнял работу;
- структурированный PASS/FAIL;
- evidence.

Критерий готовности: офис не объявляет DONE без успешной проверки.

### Этап 5 — Recovery
- Failure Classifier;
- Fix;
- Retest;
- retry budget;
- остановка при неисправимой ошибке.

Критерий готовности: намеренная ошибка проходит цикл FAIL → FIX → RETEST.

### Этап 6 — Live Monitor
- сотрудники;
- текущая задача;
- состояния;
- AI/tool ошибки;
- retries/fallback;
- recovery;
- evidence;
- история выполнения.

Критерий готовности: весь реальный прогон виден в мониторе без ручного объяснения.

### Этап 7 — OpenAI provider
- OpenAI через существующий AI Gateway;
- отдельный сотрудник/мозг;
- конфигурация без изменения ядра;
- реальный smoke-test после появления API key.

## Правила проекта

- Не считать UI доказательством выполнения: доказательством являются backend events + tool results + verification evidence.
- Не объявлять DONE по одному ответу LLM.
- Не смешивать управление с рабочими файлами: код и артефакты живут в GitHub/облаке.
- Каждый этап сначала имеет критерий готовности, затем код, затем реальный тест.
- Не переходить к следующему этапу, пока критерий текущего не подтверждён.
- OpenAI не является блокером: текущий MVP строится на Gemini, OpenAI подключается через Gateway позже.
