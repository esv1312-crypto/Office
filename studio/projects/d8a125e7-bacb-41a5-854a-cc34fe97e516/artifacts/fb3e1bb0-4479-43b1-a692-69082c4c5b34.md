## Analysis: Failed-Task Redispatch and Worker Tool Budgets

### 1. Why Failed Tasks Are Not Redispatched

**Source:** `studio/director/director-dispatch.js`, lines 50–74

The `dispatch` function iterates over `loaded.tasks` and branches on `task.status`. The status matrix is:

| Task status | Handling | Line range |
|---|---|---|
| `assigned` | "Resume" path — but **no actual re-submission** | 53–68 |
| `running` | Skipped | 69–71 |
| `qa` | Skipped | 69–71 |
| `completed` | Skipped | 69–71 |
| `planned` | Fresh assignment via `chooseSpecialist` + `assignment.assign()` | 75–103 |
| `ready` | Fresh assignment (skips `markTaskReady`) | 75–103 |
| **Any other status** (e.g., `failed`) | **Blocked permanently** — `"Unexpected task status"` | 72–74 |

**Two distinct failure modes:**

**a) The "assigned" branch is cosmetic, not functional (lines 53–68).**
The comment states: *"Re-submit the existing assignment to the Worker Pool so its durable execution store can start a fresh attempt."* However, the code only pushes `{ taskId, specialistId, taskStatus: "assigned", resumed: true }` into `report.assigned`. **No call to `assignment.assign()` or any worker-pool submission is made.** The task remains in `assigned` state with no fresh execution started. The "redispatch" is a reporting artifact.

**b) No `failed` status branch exists (lines 72–74).**
If a task transitions to a `failed` status (which the durable execution store presumably sets when the tool loop throws), it hits:
```javascript
if (task.status !== "planned" && task.status !== "ready") {
  report.blocked.push({ taskId: task.id, reason: `Unexpected task status: ${task.status}` });
  continue;
}
```
The task is permanently blocked with no path to retry. It will never be redispatched unless an external operator manually resets its status.

**c) No retry accounting.** There is no `attemptCount`, `nextRetryAt`, or backoff logic anywhere in the dispatch path. Even if a task were transitioned back to `ready`, there is no hard ceiling on how many times it can cycle through dispatch → fail → reset → dispatch again.

### 3. Proposed Bounded Retry Policy with Hard Ceiling

#### Design

Introduce a retry-aware dispatch path that:

1. **Adds a `failed` status branch** that transitions the task back to `ready` for reassignment, rather than blocking it permanently.
2. **Tracks retry state** in the task record (via the durable store): `retryCount` and `nextRetryAt`.
3. **Enforces a hard ceiling** of `MAX_RETRIES = 3` total attempts per task.
4. **Applies exponential backoff** with jitter: `delay = min(1000 * 2^attempt, 30000) + jitter(±25%)`.
5. **Circuit-breaks** after the ceiling is reached: marks the task as `blocked` with code `TASK_RETRY_CEILING_EXCEEDED` and does not attempt further dispatch.

#### Minimal Fix Strategy

**File: `studio/director/director-dispatch.js`**

Replace lines 72–74 (the catch-all "Unexpected task status" block) with:

```javascript
// Lines 72-74 replacement proposal
if (task.status === "failed") {
  const attemptCount = Number(task.retryCount || 0) + 1;
  const MAX_RETRIES = 3;
  if (attemptCount > MAX_RETRIES) {
    report.blocked.push({
      taskId: task.id,
      code: "TASK_RETRY_CEILING_EXCEEDED",
      reason: `Task failed after ${attemptCount} attempts (ceiling: ${MAX_RETRIES})`,
      retryCount: attemptCount,
    });
    continue;
  }
  // Exponential backoff with jitter
  const baseDelay = Math.min(1000 * Math.pow(2, attemptCount - 1), 30000);
  const jitter = Math.random() * baseDelay * 0.5;
  const nextRetryAt = new Date(Date.now() + baseDelay + jitter).toISOString();
  
  // Reset task to ready for reassignment
  try {
    const reset = await store.resetTaskForRetry({
      taskId: task.id,
      expectedVersion: task.version,
      retryCount: attemptCount,
      nextRetryAt,
      at: now(),
      actorId: actor?.id || null,
    });
    report.assigned.push({
      taskId: task.id,
      specialistId: null, // Will be chosen below
      taskStatus: "ready",
      retryCount: attemptCount,
      nextRetryAt,
      resumed: true,
    });
    // Continue to chooseSpecialist assignment below
  } catch (error) {
    report.blocked.push({
      taskId: task.id,
      code: error?.code || "TASK_RESET_FAILED",
      reason: String(error?.message || error).slice(0, 500),
    });
    continue;
  }
}
if (task.status !== "planned" && task.status !== "ready") {
  report.blocked.push({ taskId: task.id, reason: `Unexpected task status: ${task.status}` });
  continue;
}
```

**New store method required:** `store.resetTaskForRetry({ taskId, expectedVersion, retryCount, nextRetryAt, at, actorId })` — atomically transitions a `failed` task to `ready`, increments `retryCount`, and sets `nextRetryAt`. Must be an optimistic-concurrency operation using `expectedVersion`.

**Gateway-level hard ceiling enforcement** (`studio/gateways/openai-compatible-gateways.js`): The existing limits (`maxTotalOutputTokens = 12000`, `maxTotalPromptTokens = 120000`, `maxToolCalls = 24`) already act as a hard ceiling per execution attempt. No change needed; these are already fixed and enforced.

#### Regression Scenario

**Scenario:** A task fails during execution (tool loop throws `TOOL_CALL_BUDGET`). The durable store sets `task.status = "failed"` and persists `retryCount = 0`.

1. **Before fix:** Dispatch sees `status = "failed"`, hits the catch-all, pushes to `report.blocked` with `"Unexpected task status: failed"`. Task is dead forever. **Result: permanent failure.**

2. **After fix:** Dispatch sees `status = "failed"`, computes `attemptCount = 1 ≤ 3`, calls `store.resetTaskForRetry()` to set status back to `ready` with `retryCount = 1` and a backoff `nextRetryAt`. The task then flows into the normal `chooseSpecialist` + `assignment.assign()` path. **Result: task is retried with backoff.**

3. **After 3 failures:** `attemptCount = 4 > 3`, task is blocked with `TASK_RETRY_CEILING_EXCEEDED`. **Result: bounded failure with clear diagnostic.**
