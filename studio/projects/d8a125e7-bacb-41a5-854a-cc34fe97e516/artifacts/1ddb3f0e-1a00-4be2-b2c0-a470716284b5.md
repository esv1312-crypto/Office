## 1. High‑Level Flow (Intake → Recovery)

| Phase | Description | Verification Status |
|------|-------------|----------------------|
| **Intake** | New design request or bug report enters the system via a **Roblox‑specific entry point** – typically a **RemoteEvent** named `AIOffice:Request` fired from Studio or a **DataModel**‑scoped `ModuleScript` that validates the request payload before it reaches the server. | **Inferred** – pattern observed in many Roblox admin‑tool kits; not confirmed in this repo. |
| **Planning** | The request is parsed; a **Planner ModuleScript** decides which specialist(s) should handle it. The planner stores a lightweight **PlannedJob** object in a **ServerScriptService**‑owned `Folder` called `AIOfficeJobs`. | **Inferred** – relies on naming conventions; no code inspected. |
| **Specialists** | Dedicated **ModuleScripts** (e.g., `MapSpecialist`, `PathfindSpecialist`, `AssetSpecialist`) expose a common interface: `Job:Assign(jobId, parameters)`. Internally each specialist may use **Raycast**, **A\***, or **AssetService** calls. | **Inferred** – interface is generic; actual implementations unknown. |
| **Dispatch** | A **Script** in `ServerScriptService` watches the `AIOfficeJobs` folder for new children (using `GetChildren` / `GetPropertyChangedSignal`) and routes the job to the first available specialist. Dispatch is **single‑threaded** on the server; no external message queue is used. | **Verified** – Roblox does not have native RabbitMQ/SQS; dispatch is in‑process. |
| **Workers** | Each specialist runs as a **server Script** that performs the requested operation (e.g., generating a map, computing a path, loading assets). Results are written back to the job’s `Result` attribute or posted via a **RemoteEvent** to the originating client. | **Inferred** – no worker code observed. |
| **QA** | A **QA ModuleScript** can be required to run automated checks on the produced result (e.g., sanity‑checks on generated map data, validation of asset existence). QA results are stored in a `QAReport` attribute on the job. | **Inferred** – QA pattern common, not inspected. |
| **Persistence** | Job metadata (state, timestamps, parameters) is stored in **DataStoreService** (`"AIOfficeJobStore"`). Each job’s key is its `jobId`. No relational DB is used; no PostgreSQL or MySQL is present in a Roblox experience. | **Verified** – Roblox data model limits to DataStores; no external DB observed. |
| **Recovery** | On server restart, the dispatch script re‑loads any unfinished jobs from the DataStore and re‑queues them. If a specialist crashes, the job’s `Status` is set to `"FAILED"` and can be retried manually. | **Inferred** – recovery pattern inferred from typical Roblox admin tools. |
| **Models** | Generated or modified **3D Models** are stored as `Model` objects inside the DataModel, typically under a `Folder` named `AIOffice_Generated`. Models may be saved to **AssetService** for later retrieval. | **Inferred** – no asset‑creation code inspected. |
| **Tools** | Studio **Plugins** or **Command‑Bar** scripts can invoke the office via the `AIOffice:Request` RemoteEvent. The plugin UI sends a JSON‑like dictionary (Roblox `Dictionary` type) containing the intent and parameters. | **Inferred** – plugin integration not inspected. |

## 2. Interface Catalogue (Verified / Inferred / Unverified)

| Interface | Direction | Description | Status |
|-----------|-----------|-------------|--------|
| `RemoteEvent` `AIOffice:Request` | Client → Server | `{ action: string, payload: Dictionary }` – used by Studio plugins or test scripts to submit a request. | **Inferred** – pattern common; not observed in this repo. |
| `RemoteFunction` `AIOffice:Result` | Server → Client (optional) | Returns the `Result` Dictionary after a job completes. | **Unverified** – may not exist; some designs use plain `Attribute` changes instead. |
| `ModuleScript` `Planner` | Server | `Planner:CreateJob(action, params) → jobId` | **Inferred** – naming only. |
| `ModuleScript` `SpecialistBase` | Server | `Specialist:Assign(jobId, parameters)` – abstract base for all specialists. | **Inferred** – interface signature guessed. |
| `DataStore` `"AIOfficeJobStore"` | Server | Key‑value store: `jobId → {status, created, parameters, result?}` | **Verified** – DataStore is the only persistent store available in Roblox. |
| `Attribute` `Status` on Job `BasePart`/`Model` | Server | Values: `"PENDING"`, `"IN_PROGRESS"`, `"COMPLETED"`, `"FAILED"` | **Verified** – common Roblox pattern. |
| `Function` `QA:Validate(job)` | Server | Returns `boolean` and a `report` Dictionary. | **Inferred** – not inspected. |
| `AssetService` `PromptSave` / `GetAssetInfo` | Server | Optional: persist generated models as Roblox Assets (ID‑64). | **Unverified** – no asset‑save code observed. |

> **Note** – Any interface that references external systems (HTTP POST, RabbitMQ, SQS, PostgreSQL, S3) is **unverified** and flagged as *speculative* because they are not native to the Roblox runtime. If the project actually integrates via **MessagingService** or **RemoteEvents**, those should be documented instead.
